# AI 生成代码审核标准与准入规程

本文件定义 SpecLock Scaffold 小组对 AI 生成代码的拆解方法、评分维度、三分法判定标准与合入主干（`main`）的准入流程，与仓库根目录 [AGENTS.md](../AGENTS.md) 第 3 节「七类核查清单」配套使用。

---

## 一、三层核查机制与分工

遵循「机器能判的交给机器，人工只聚焦机器给不出判据的语义与取舍」原则，代码审核按三层推进：

| 层级 | 执行主体 | 负责范围 | 交付产物 |
| --- | --- | --- | --- |
| **1. AI 自审** | Harness 按 `AGENTS.md` 执行 | 对照七类核查清单与分层约束逐段审查初稿，指出潜在并发、越权、失败出口与分层越界问题并附依据 | 评审初稿归档至 `reports/review-0X.md`；共性缺陷反哺写入 `AGENTS.md` 第 4 节 |
| **2. 脚本门禁** | 自动化检查命令与 CI | 分层依赖检查、单元与隔离守护进程回归用例、网关安全反例、密钥泄漏扫描、依赖漏洞审计、并发压测 | 检查命令退出码（非 `0` 直接阻断合入）及 `reports/` 下的基线与三查记录 |
| **3. 人工确认** | 组内交叉评审人（Peer Reviewer） | 仅裁决机器无法自动判定的三类事项：业务意图合理性、跨包契约变更影响、故障恢复策略取舍 | 确认结论必须转化为新自动化用例或 `AGENTS.md` 新规则，确保同类问题不再二次耗费人工 |

## 二、高风险代码四步拆解法

审核涉及状态变更、进程控制、文件落盘与权限边界的代码时，禁止笼统给出「看着没问题」，必须按以下四步拆解：

1. **它想保证什么**：明确业务或系统不变量（例如：同一实例同时间只能跑一轮任务、跨项目不能操作执行者、守护进程崩溃不丢在途记录）。
2. **它实际靠什么保证**：看代码当前依赖的机制（例如：靠内存 `Set` 互斥锁、靠 `guard.mjs` 前缀校验、还是仅靠前端隐藏按钮）。
3. **什么情况下会失效**：推演并发穿插、进程强杀、网络重试、恶意构造请求头或路径逃逸（`..`）时的边界表现。
4. **挡得住的改法**：将脆弱假设替换为底层硬约束（如唯一键检查、预写日志 `journal.mjs` 启动对账、`resolveInside` 绝对路径收敛、网关与守护进程双层拦截），并补齐反例测试。

## 三、本组评审表（七维度核对 + 三分法结论）

每次提交合入评审时，审核人按以下七个维度逐项核对：

| 评审维度 | 核对内容与判据 | 状态（通过 / 缺陷 / 不涉及） |
| --- | --- | --- |
| **1. 需求与规格覆盖率** | 对照目标需求或规格验收条件（AC）逐条核验：已完整实现且有对应验证证据，无遗漏分支 | |
| **2. 架构与契约一致性** | 符合 `ARCHITECTURE.md` 分层规则；`layers-test.mjs` 通过；跨包接口与事件格式保持兼容 | |
| **3. 失败路径覆盖** | 非法输入、子进程崩溃、工具卡死、超时取消、磁盘读写异常均有明确错误处理与资源回收出口 | |
| **4. 性能与资源边界** | 无无界内存累积或全量阻塞读取；长记录走 `afterSeq` 游标或头尾裁剪；子进程受池上限与进程树清理约束 | |
| **5. 重复代码控制** | 公共能力（RPC、进程树销毁、路径校验、配置加载）复用既有基础模块，无跨文件复制粘贴 | |
| **6. 安全与隐私合规** | 通过本地 `Host`/`Origin` 校验、项目作用域隔离、路径防逃逸、命令注入拦截及密钥脱敏检查，无明文凭证入库 | |
| **7. 高风险场景核查** | 触及**并发、事务/崩溃一致性、权限隔离**的变更，已补充或通过对应的专项可复跑用例 | |

### 三分法判定标准与后续动作

| 判定结论 | 适用条件 | 强制后续动作 |
| --- | --- | --- |
| **可用** | 七个维度全部通过，符合架构约束与安全要求，自动化测试全绿 | 归档评审记录，准予合入 `main` 分支 |
| **待修改** | 整体方向正确，但存在边界漏判、错误处理缺失、分层越界或测试覆盖不足 | 列出具体修改项与代码位置，修复并补齐用例后重新触发审核 |
| **风险无效** | 存在跨项目越权、命令注入、明文密钥泄漏、并发数据错乱或偏离核心需求 | 直接废弃打回重写，严禁「带病凑合合入」 |

## 四、主干准入流程与评审记录规范

1. **准入流水线**：`AI 在 AGENTS.md 约束下生成初稿` → `作者本地跑通隔离回归测试与逐段自审` → `AI 自审 / 组员交叉评审并留痕` → `脚本门禁全绿后合入 main`。
2. **评审记录四要素**：每份归档至 `reports/review-0X.md` 的记录必须写清以下四项可复核事实，不写主观感受：
   - **检查手段**：执行的测试脚本命令、AI 自审加载的规则章节，或人工复核的具体模块。
   - **检查对象**：具体到文件路径、接口路由或状态流转环节。
   - **判定依据**：对照的规约条款、`AGENTS.md` 核查项或断言条件（如期望状态码、唯一性结果）。
   - **发现与闭环结果**：先红后绿的现象对比、修复提交的改动点，以及固化下来的常驻测试用例或新增规则。
